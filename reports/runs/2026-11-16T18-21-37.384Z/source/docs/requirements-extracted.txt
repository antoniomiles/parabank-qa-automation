PRUEBA TÉCNICA PRÁCTICA   –   QA AUTOMATION 
Duración sugerida:   3 horas 
Puntaje máximo:   120 puntos 
1. Instrucciones generales 
•   Utilice Playwright o Cypress para la automatización web y Postman o código para las pruebas de API. 
•   Utilice Apache JMeter para construir un plan de pruebas de rendimiento.   No ejecute carga. 
•   Guarde el proyecto en un repositorio GitHub o GitLab y comparta un enlace accesible al evaluador. 
•   Incluya un archivo README con requisitos, comandos de ejecución y aclaraciones sobre pruebas
que no pudo ejecutar. 
•   Adjunte las evidencias disponibles (reportes, capturas, resultados y scripts). Las fallas reales del
aplicativo deben quedar documentadas, no ocultarse. 
•   No se permite usar herramientas de IA. 
2. Caso práctico: Pago de servicios desde banca web 
Una institución financiera necesita validar el proceso de pago de servicios que realiza un socio desde su
cuenta bancaria. El socio inicia sesión, selecciona el módulo de pagos, completa los datos del
beneficiario, elige su cuenta y confirma el monto. Posteriormente consulta los movimientos de su
cuenta. 
Aplicación de práctica:   ParaBank   –   https://parabank.parasoft.com/parabank/index.htm 
Documentación de servicios:   https://parabank.parasoft.com/parabank/api-docs/index.html 
Reglas de aceptación para el ejercicio (se deben contrastar con el comportamiento real de la aplicación): 
•   El acceso a operaciones bancarias requiere un usuario autenticado. 
•   Se debe completar la información obligatoria del pago. 
•   El monto debe ser mayor que cero. 
•   Si el pago se completa exitosamente, debe quedar evidencia de la operación y debe poder verificarse
el movimiento correspondiente. 
•   Un pago rechazado no debe tratarse como una operación exitosa. 
Nota: las reglas anteriores son parte del escenario de evaluación. Si alguna no coincide con ParaBank,
documente el hallazgo o limitación; no altere el aplicativo ni invente resultados. 
3. Ejercicio práctico 
A. Diseño de casos de prueba   –   15 puntos 
Elabore como mínimo cinco casos de prueba del flujo de pago (positivos, negativos y regresión). Incluya
ID, escenario, precondiciones, datos, pasos, resultado esperado, prioridad y criterio de aceptación
relacionado. Seleccione y justifique los escenarios que automatizará. 
Entregable: archivo de casos de prueba (Excel o CSV).

B. Automatización web   –   25 puntos 
Desarrolle y ejecute, con Playwright o Cypress, al menos tres pruebas automatizadas del punto anterior
y los siguientes casos: 
•   Inicio de sesión con credenciales válidas del entorno de demostración. 
•   Pago de un servicio con datos válidos y comprobación del resultado mostrado. 
•   Validación de un escenario negativo del formulario de pagos. 
Las pruebas deben contener aserciones, datos de prueba organizados y elementos reutilizables cuando
corresponda. Evite esperas fijas innecesarias. 
Entregable: código ejecutable, instrucciones y reporte/capturas de ejecución. 
C. Pruebas API   –   20 puntos 
Seleccione y automatice al menos dos operaciones REST documentadas de ParaBank, relacionadas con
cuentas, pagos o movimientos. Incluya aserciones de estado y contenido de respuesta, además de una
verificación de datos del negocio. 
Entregable: colección Postman exportada con pruebas o código de automatización API, más evidencia
de ejecución. Si una API no está accesible, registre el endpoint, solicitud, error y alternativa propuesta. 
D. Pipeline automatizado   –   15 puntos 
Prepare un workflow de GitHub Actions o equivalente que instale dependencias, ejecute las pruebas
automatizadas, muestre correctamente los resultados y conserve reportes como artefactos. No oculte
fallos de pruebas para forzar un resultado exitoso. 
Entregable: archivo YAML, instrucciones y enlace/captura de ejecución cuando sea posible. 
E. Resultados, evidencias y defectos   –   5 puntos 
Incluya un resumen de pruebas ejecutadas, aprobadas, fallidas y bloqueadas. Si encuentra defectos,
documente título, pasos reproducibles, esperado, obtenido, severidad y evidencia. No es obligatorio
encontrar defectos reales en la aplicación pública. 
Entregable: informe breve de ejecución y defectos o limitaciones documentadas. 
F. Plan de rendimiento en Apache JMeter   –   20 puntos 
Elija una API REST de consulta de ParaBank que considere apropiada para evaluar rendimiento.
Justifique su selección por frecuencia de uso, importancia y riesgo. Cree un archivo .jmx que incluya
HTTP Request, variables o parámetros, aserciones y listeners apropiados. 
Configure dos escenarios: 
•   Escenario 1 (carga base): usuarios virtuales, con ramp-up e iteraciones por usuario. 
•   Escenario 2 (carga incremental): usuarios virtuales, con ramp-up e iteraciones por usuario. 
Describa qué métricas examinaría: promedio, percentil 95, throughput y porcentaje de errores. El script
debe quedar listo para ejecutar en un entorno autorizado. No ejecute pruebas de carga ni estrés contra
ParaBank.

G: Automatización mobile   –   20 puntos 
Elige una herramienta para automatizar en versión mobile y describe cuáles son los pasos para
automatizar en app . 
4. Entrega final 
Comparta un repositorio con una estructura clara (por ejemplo: /casos, /web, /api, /performance,
/evidencias, /pipeline y README.md). El README debe indicar qué actividades se completaron, cómo
reproducirlas y qué obstáculos o limitaciones encontró. 
El enlace del repositorio deberá ser enviado a la persona de talento humano.
